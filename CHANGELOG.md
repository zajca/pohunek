# Changelog

User-facing changes of pohunek.

## 0.40.1 - 2026-11-06

### Added

- `cargo xtask index check-entry` checks one added plugin index entry against the admitted entries and the pinned core: the package id must be `pohunek.runtime.` plus the runtime id, the runtime id must not be one of the refused ids, the version must be a release above every admitted version, and the core range must admit the pinned core with a lower bound of at least 0.40.0. A refusal names its predicate. The index repository's admission workflow runs it. ([#1937](https://github.com/zajca/pohunek/issues/1937))

## 0.40.0 - 2026-11-06

### Added

- A runtime can declare `[runtime] trusted_checkout_args` and `trusted_checkout_paths` (feature `checkout-trust-args-v1`): the daemon appends the arguments at create, resume and fork only for a clean checkout of a GitHub repository listed in the new `service.toml` `[checkout_trust] trusted_repositories`, whose declared paths equal the tree of the remote `HEAD` commit. Any git error or missing fact withholds them. ([#1925](https://github.com/zajca/pohunek/issues/1925)) ([#1925](https://github.com/zajca/pohunek/issues/1925))
- The package crate verifies a signed plugin index: a separate document family from the runtime catalog, endorsed directly by one designated offline root, with embedded key revocation, a sequence at most one day ahead of the clock and a lifetime of at most 14 days. Nothing installs from an index yet; the daemon and CLI wiring follow. ([#1929](https://github.com/zajca/pohunek/issues/1929)) ([#1929](https://github.com/zajca/pohunek/issues/1929))
- The package crate persists the per-host plugin index state (`index-state.json`: index and revocation high-water marks plus the accumulated revoked key ids, merged only upward under the registry lock) and parses `plugin-index-channel.json`, the release file that names the index endorser root of the trust anchor. Nothing reads them yet; the daemon and CLI wiring follow. ([#1930](https://github.com/zajca/pohunek/issues/1930)) ([#1930](https://github.com/zajca/pohunek/issues/1930))
- The daemon installs a package authorized by a signed plugin index: `package.install` accepts the `index` trust kind, verifies the index against the endorser root named by `plugin-index-channel.json` beside the trust anchor, persists the index marks before the install and refuses commands and the runtime ids `shell`, `codex`, `claude`, `hermes` and `pi`. `host.inspect` reports `package_install_index_supported` and `daemon.doctor` reports the `plugin_index_channel` check. ([#1931](https://github.com/zajca/pohunek/issues/1931)) ([#1931](https://github.com/zajca/pohunek/issues/1931))
- `pohunek plugin install` accepts `--index <file>` beside `--sha256` and `--catalog`, and installs by package id: `pohunek plugin install <package-id>[@<version>]` fetches the official plugin index (or `--index-url`) and the archive it lists, checks the digest and lets the daemon verify both. The review names the resolved version and the command to repeat pins it. `plugin update` accepts `--index <file>`. ([#1932](https://github.com/zajca/pohunek/issues/1932)) ([#1932](https://github.com/zajca/pohunek/issues/1932))
- Daemon archives ship `plugin-index-channel.json` beside the trust anchor, and `pohunek service install` and `upgrade` copy it into the version directory like the anchor. A version directory published by an older CLI without the file is reported as `service_version_lacks_index_channel` when a 0.40 CLI runs the same version again; installs by plugin id stay off for it until the next release or a reinstall from the archive. ([#1933](https://github.com/zajca/pohunek/issues/1933)) ([#1933](https://github.com/zajca/pohunek/issues/1933))
- `cargo xtask` gains the owner ceremony commands of the plugin index: `catalog keygen` creates an owner-private Ed25519 key file, `index endorse` signs the `official` record of an index key, `index revoke` writes the next revocation list (it never shrinks), and `index channel` writes the channel file for a root of the trust anchor. Keys are read only from files and never printed, outputs are created exclusively, and every document is verified with the daemon's rules before it is written. The key ceremony and compromise procedure are in the new plugin index keys runbook. ([#1934](https://github.com/zajca/pohunek/issues/1934)) ([#1934](https://github.com/zajca/pohunek/issues/1934))
- `cargo xtask index` gains the tooling that produces a signed plugin index without any key reaching the process: `build` turns an entries tree (`official/<package_id>/<version>.toml`, with a validated `[source]` table that stays out of the document) into an unsigned index, `message` writes the bytes an external signer signs, `attach` inserts that signature after the daemon's own verifier accepted the result, and `verify` checks a signed index, or a key record and a revocation list, with the same rules. `throwaway` creates a self-contained trust root and a signed index for proofs. The checks live in the package crate, so the tool and the daemon cannot disagree. ([#1935](https://github.com/zajca/pohunek/issues/1935)) ([#1935](https://github.com/zajca/pohunek/issues/1935))
- `cargo xtask plugin build` writes the canonical, byte-reproducible archive of a plugin's package directory, `cargo xtask plugin prove` installs an archive through the plugin index path on an isolated daemon without launching the runtime and records the verdict as evidence, and the reusable `plugin-release.yml` workflow builds, attests and publishes a plugin release from a version tag. ([#1936](https://github.com/zajca/pohunek/issues/1936)) ([#1936](https://github.com/zajca/pohunek/issues/1936))
- Runtime descriptors can declare how a session stays out of a shared host daemon with a `[placement]` table (runtime feature `placement-v1`), and the session worker reports a process that left the terminal's session as a daemon: `session inspect` shows a `placement` row (`placement_escape` with pid and command name) and `pohunek doctor` a `placement_escape` check. The check is report-only and kills nothing. The Claude Code, Codex, Pi and Hermes packages declare their placement (1.3.0, 1.6.0, 1.2.0 and 1.1.0). ([#1947](https://github.com/zajca/pohunek/issues/1947))
- The Cline CLI package can keep a Pohunek session in the terminal's process tree and report its identity and subagents: runtime feature `integration-cline-hook-v1` adds the `cline-hook-v1` integration handler, which launches Cline in sandbox mode on the user's data root, follows `/clear` and `/fork` at the next turn, journals subagents, and installs one reporter as the six Cline hook files in `<CLINE_DIR>/hooks/`. `pohunek integration install` refuses, and leaves untouched, a file that is not Pohunek's at one of those paths, and `uninstall` removes only Pohunek's files. ([#1953](https://github.com/zajca/pohunek/issues/1953))

### Changed

- The daemon's runtime package lifecycle (install, link, enable, select, uninstall, profile bind) now lives in its own `PackageAuthority` under `crates/daemon/src/packages/` instead of the session registry. No behavior or wire change. ([#1627](https://github.com/zajca/pohunek/issues/1627)) ([#1627](https://github.com/zajca/pohunek/issues/1627))
- The Claude Code package guide now documents `CLAUDE_CODE_FORCE_SYNC_OUTPUT = "1"` in a profile `[env]`, which lets clients that draw between PTY reads, such as the Android companion, avoid torn frames. The variable is undocumented by Anthropic and may change. ([#1840](https://github.com/zajca/pohunek/issues/1840))
- Codex sessions are launched with `--no-daemon` by the `codex-hook-v1` integration handler on every create and resume, profile sessions and sessions created earlier included, so two Pohunek Codex sessions on one `CODEX_HOME` no longer share Codex's managed app-server daemon: each session's hooks report to its own worker, and stopping one session no longer strands the other. The Codex package (1.5.0) now supports Codex from 0.164.0, the first release verified with the flag. ([#1943](https://github.com/zajca/pohunek/issues/1943))
- The checkout trust documentation names the on-disk refusals (an entry that differs from a declared component only by letter case, a declared path the file system opens under another spelling) and the shared 30 second deadline of the git calls and the on-disk walk. ([#1985](https://github.com/zajca/pohunek/issues/1985)) ([#1985](https://github.com/zajca/pohunek/issues/1985))

### Fixed

- A session whose worker stopped answering `session screen`, `session input` and `session stop` after an output burst and a large input is no longer wedged. The daemon now reads the worker connection continuously, closes a connection whose request or answer does not finish (new optional `service.toml` keys `worker_send_ms` and `worker_answer_ms`), and `session stop` ends a worker that does not answer through its service manager. ([#1983](https://github.com/zajca/pohunek/issues/1983))

## 0.39.0 - 2026-11-02

### Added

- `pohunek service refresh-path [--dry-run] [--json]` re-records the executable search path from your login shell, as install would record it now, and prints the directories it adds and removes (`--dry-run` stops there). Use it after installing an agent prefix later or after a Nix profile update moved the profile link; `service check` and `service upgrade` judge runtimes with the new path at once. A path that is already current changes nothing. A login shell that fails, hangs or prints junk never replaces the recorded path. New error codes: `service_search_path_refresh_failed` (the login shell gave no usable path), `service_search_path_unmanaged` (the host records no path, such as the Linux user manager), `service_refresh_blocked_by_transaction` (an install or upgrade is pending) and `service_refresh_config_schema` (`service.toml` is of another schema than this release writes; nothing is rewritten). ([#319](https://github.com/zajca/pohunek/issues/319))
- A lost session runtime now says why. `runtime.exit` of an OOM-killed worker names the memory killer (`oom_killer`: `kernel` or `systemd_oomd`, only when exactly one is evidenced) and carries the unit's peak memory (`memory_peak_bytes`) and end time (`ended_at`). A loss with no service-manager verdict carries `runtime.loss_cause`: `user_manager_lost` when the systemd user manager that held the worker is gone, `host_restarted` after a reboot. The fields are additive on protocol 4 and absent on protocol 3; the metadata store moves to schema 15 (a no-op migration), so a release that predates it refuses the store and a rollback restores the `metadata.jsonl.pre-schema-<previous>` backup. ([#422](https://github.com/zajca/pohunek/issues/422))
- A named pohunek session now passes its name to Claude Code (`claude --name=<name>`) at launch, resume and fork, so Claude shows the name in its prompt box and terminal title; the Claude package needs pohunek 0.39. Two live Claude sessions with one name keep both names unique on Claude's side (`<name>-<adjective>-<noun>`). ([#979](https://github.com/zajca/pohunek/issues/979))
- A runtime package can pass the pohunek session name to its agent at launch, resume and fork with `[naming] launch_args` (runtime feature `naming-launch-args-v1`), either joined into one `-<flag>=` token (`--name={session_name}`) or as a separate element after a flag (`["--name", "{session_name}"]`). In the separate form a name that starts with `-` is not passed at all, so an agent can never read it as an option. The official Claude and Pi packages declare it. ([#979](https://github.com/zajca/pohunek/issues/979))
- A named pohunek session now passes its name to Pi (`pi --name <name>`) at launch, resume and fork, so Pi shows it in its footer and terminal title; the Pi package 1.1.0 needs pohunek 0.39. ([#979](https://github.com/zajca/pohunek/issues/979))
- A session now records which session created it. When `session.new` or `session.fork` arrives with the request origin pair (the CLI and the Rust client send the inherited `POHUNEK_SESSION_ID` and `POHUNEK_DAEMON_ID`; the TypeScript SDK sends it when `ConnectOptions.origin` is set), the daemon stores it as the immutable `spawned_by` (`session_id`, `daemon_id`) of the new session, and `SessionInfo` reports it in `session.inspect`, `session.list` and events. `pohunek session list --spawned-by <session-id>` lists the sessions one session spawned and combines with the other list filters. The link is attribution recorded by the host from the request origin, not a security boundary: a process of the same user can omit the origin variables. The session store moves to schema 13 (a release that predates it refuses the newer store; the migration keeps a `.pre-schema-<previous>` backup), and a protocol 3 client does not see the field, while the current CLI (`--spawned-by`), Rust client and TypeScript SDK refuse the `spawned_by` filter against a protocol 3 daemon before sending it. ([#1300](https://github.com/zajca/pohunek/issues/1300))
- `pohunek session new --request-id <id>` makes a creation idempotent: repeating the command with the same id returns the session the first one created (`--json` then carries `replayed: true`) instead of creating a second one, and a host whose daemon does not advertise `session_new_request_id_supported` is refused with `session_new_request_id_unsupported` before anything is sent. `pohunek assistant` takes the same `--request-id`, sends a generated one on every launch against a daemon that supports it, and repeats an unanswered creation once within the same `--request-timeout-ms` deadline; an outcome that stays unknown names the id so rerunning the same command with `--request-id <id>` can get the session back on a local host (a remote host picks a new snapshot path for every launch, so look the session up by `--meta` there). Against a daemon without the flag nothing changes: one request, never resent. ([#1340](https://github.com/zajca/pohunek/issues/1340))
- `session.new` accepts an optional `client_request_id` (1 to 128 bytes of `[A-Za-z0-9._:-]`) that makes the create idempotent. The daemon persists the key with a fingerprint of the request on the session's record (store schema 14); a repeated key with the same request returns the existing session with `replayed: true` and runs no hook and injects no input, the same key with another request fails with `session_request_conflict`, and a key whose create has not settled fails with `session_request_in_progress`. A rolled-back create, `session remove` and retention free the key. The fingerprint covers every parameter except the key, `cols`, `rows` and the `secret_env` values. A daemon advertises `session_new_request_id_supported` in `host.inspect`; the Rust client and the TypeScript SDK refuse to send a key to a daemon without it (`session_new_request_id_unsupported`), and protocol 3 peers refuse it with `daemon_protocol_too_old`. A release that predates schema 14 refuses the newer store; roll back with the `metadata.jsonl.pre-schema-<previous>` backup the migration takes (sessions created since are lost) or keep the newer release. ([#1340](https://github.com/zajca/pohunek/issues/1340))
- On macOS a lost session now records why its worker ended. The daemon watches each worker process through the kernel and reports a non-zero exit code, a terminating signal, or a kill under memory pressure in `runtime.exit` (`pohunek session inspect`), as it already did on Linux. A worker that ended while the daemon was not running still has no recorded cause. ([#1343](https://github.com/zajca/pohunek/issues/1343))
- On Apple Silicon Macs with a stock Homebrew prefix, Pohunek now finds the `tailscale` CLI from `brew install tailscale` in `/opt/homebrew/bin`, so `pohunek doctor` and `host list` report the Tailscale state instead of a missing CLI. Pohunek does not start `tailscaled`. No part of a running `tailscaled` is verified on macOS, neither the client side nor the listener on the tailnet address. The App Store and standalone builds are still refused. ([#1583](https://github.com/zajca/pohunek/issues/1583))
- `pohunek store rejected list` shows the `metadata.jsonl` lines no loader accepts (kind, line number, reason, whether they may pin a package) and `pohunek store rejected set-aside <content-hash>` moves one into the owner-private `metadata.rejected.jsonl` with an audit record; a line that may own a live runtime, or a `resume` line whose pin cannot be read, needs `--accept-pin-loss`. The methods `store.rejected_list` and `store.rejected_set_aside` are local-only and new in protocol 4. `pohunek doctor` reports rejected lines and names the command, and the offline `plugin ensure` path judges a kept rejected line like the daemon gates: it never reads a digest from it, reports the plan as uncertain and fails closed where a pin may be lost. ([#1651](https://github.com/zajca/pohunek/issues/1651))
- `pohunek service refresh-path [--accept-runtime-loss]` also replaces the daemon job with the re-recorded search path, so the running daemon gets the new `PATH` at once. The path in `service.toml` and the daemon job change together in one journaled transaction or not at all; only the daemon restarts and worker jobs keep running. The new daemon's adoption verdict is taken first, as for an upgrade: live sessions it would not adopt refuse the run unless `--accept-runtime-loss` is given, which records nothing. Readiness requires a new daemon process, and a replacement or readiness failure restores the previous path and job. An interrupted run is resumed by rerunning the command, or rolled back; from the replacement step on, the pending record blocks `install` and `upgrade` until `refresh-path` completes or rolls it back. In production the daemon replacement runs on macOS only. New error codes: `service_daemon_job_missing` (no registered daemon job), `service_refresh_config_changed` (`service.toml` was edited while a refresh was pending) and `service_refresh_pending` (a pending refresh blocks the command). ([#1758](https://github.com/zajca/pohunek/issues/1758))
- `pohunek doctor` on macOS reports `service_search_path_agents` (`warn`) when `claude` or `codex` resolves through your login shell's search path but not through the one recorded in `service.toml`, which the daemon runs with; the detail names the program and the remedy `pohunek service refresh-path --dry-run`. The probe is bounded, takes no transaction lock, and reports nothing when the login shell fails or hangs, on a host that records no path or an empty one, without an installation that loads and verifies, or while a transaction record is pending. Doctor waits for the probe for at most the login-shell timeout. ([#1761](https://github.com/zajca/pohunek/issues/1761))
- `pohunek service upgrade --repair` recovers a refused (`service_version_untrusted`) or missing active version directory without uninstalling: run it from the release archive of that version with `--from`. The refused entry is renamed to `.pohunek_refused-<version>-<random>` in the versions directory and kept, the release's staged copy is published in its place, `service.toml` and the worker jobs are not touched, and the daemon job is started, registered again, or restarted as a new process after the adoption preflight. A missing directory is published without the flag, an upgrade that rolls back to or resumes at a refused or missing directory gets the same repair, and `pohunek service install --repair` resumes an interrupted install the same way. `pohunek service uninstall` over an untrusted active directory and live workers now says which version to restore and how, and lists the entries repairs moved aside. The hints of `service_version_untrusted` and of `pohunek daemon start` name the command. A `refresh-path` stopped at `registering`, or rolling back from `registering` on, over such a directory is repaired in two steps: `upgrade --repair --from` restores the directory before it refuses with `service_refresh_pending`, then `refresh-path` finishes the refresh or its rollback. ([#1763](https://github.com/zajca/pohunek/issues/1763))

### Changed

- `pohunek session list` and `session inspect` show one state for a session whose runtime was lost, `crashed`, whether or not the loss is proven, with the readable cause (the memory killer and peak, the signal or exit code, the loss of the user service manager, or a host restart) and whether `session resume` can bring it back. The notification for a lost runtime carries the same cause: "Session crashed" for a proven loss, "Session runtime lost" for an unproven one, once per loss, so a runtime that answers again and is lost again is reported again. The TypeScript SDK gains `sessionCondition()` with the same rule. `--json` output is unchanged. ([#422](https://github.com/zajca/pohunek/issues/422))
- Fire-and-forget `session.input` to a Pi session that reads `blocked` is refused with `session_input_blocked`, and the error now carries a hint to answer the dialog in an attached terminal (`pohunek attach`). A runtime descriptor can declare this with `[input] refuse_while_blocked` (Pi package 1.0.5; Claude and Codex keep delivering text). It applies to Pi sessions started on 1.0.5: a session launched earlier keeps its pinned definition until it is relaunched or resumed. The store schema is now 12: a daemon of the previous release refuses the newer store, so roll back with the `metadata.jsonl.pre-schema-11` backup. ([#911](https://github.com/zajca/pohunek/issues/911))
- `pohunek assistant` renders the safety rules and navigation steps of its opening prompt from the knowledge bundle's `assistant/system.md`, so the prompt and the bundle cannot diverge, and no longer claims a live daemon state or a redacted snapshot: the snapshot file holds launch metadata only and is not redacted, so keep secrets out of the request. The assistant is told never to create or modify hooks in a non-interactive context instead of writing them to a quarantine path that nothing read. ([#1292](https://github.com/zajca/pohunek/issues/1292))
- The per-kind notification policy is a map from kind to flag with the same JSON, so a client of this release keeps a kind a newer daemon adds, lists a notification of such a kind as `unknown` and sends the kind back on `notifications policy set`. The daemon still refuses an unknown kind in params and in `policy.json`, and a kind the policy leaves out takes the daemon's default, so `notification.policy.get` and `notifications policy get` return a flag for every kind. The generated TypeScript `NotificationKindPolicy` has an optional key per kind. ([#1332](https://github.com/zajca/pohunek/issues/1332))
- A client now keeps a key it does not know in the session capabilities of a listed session and in the session and notification retention and policy documents a newer daemon returns, so `session list` no longer fails on a newer capability and `session policy set` and `notifications policy set` send every key back instead of resetting a setting they do not know. The daemon still refuses such a key in params, in the session store and in `policy.json` and `session-policy.json`, and a document with no unknown key serializes exactly as before. ([#1332](https://github.com/zajca/pohunek/issues/1332))
- A client now ignores a key it does not know in a daemon result, event or error: `ProtocolError` (so an error response from a newer daemon keeps its typed class, code and message instead of becoming a `json_error`), the `session.read`, `session.screen`, `session.output`, `session.wait`, `session.wait_turn` and `session.detection` results, their nested terminal cursor, runtime identity, output gap and turn event and progress records, and the `session.report_native_id`, policy and unconfirmed-process results. The types that deny unknown keys keep doing so (the strict params, persisted capabilities and policies, governance state, the envelope framing). A field is added to these types only after the next protocol bump or when only clients of this release can receive it. ([#1332](https://github.com/zajca/pohunek/issues/1332))
- A notification store that a build cannot read safely (a newer format, an undecodable action line or a rejected `policy.json`) no longer stops the daemon. The notification RPCs answer `notifications_unavailable`, the files are left untouched, and the daemon logs the reason and the remedy. The store now carries a `notifications/format.json` marker, and a guard fails when its shape changes without a format bump. ([#1333](https://github.com/zajca/pohunek/issues/1333))
- `pohunek session list` and `session inspect` no longer fail on a runtime state that a newer daemon adds: it reads as `unknown`, the session counts as possibly live (`service uninstall` refuses while it exists), and `session stop` and `session rm` refuse it locally with `session_runtime_state_unknown`. ([#1336](https://github.com/zajca/pohunek/issues/1336))
- `pohunek session` no longer fails on a runtime inventory status, retention reason or hold, wait or turn-wait reason, detection region or read source that a newer daemon adds: the value reads as `unknown` (an unknown detection region is dropped from the supported list). `session wait` exits non-zero with `session_wait_reason_unknown` when it cannot tell whether the condition matched. ([#1337](https://github.com/zajca/pohunek/issues/1337))
- `pohunek plugin` no longer fails on a package origin, fault, selection block reason, install status, profile bind status or doctor finding kind that a newer daemon adds: the value reads as `unknown`. The official-downgrade guard of `plugin update` and the consent prompt of `plugin profile migrate` stay on for an unknown value, and `plugin doctor` still exits non-zero for an unknown finding. ([#1338](https://github.com/zajca/pohunek/issues/1338))
- `pohunek notifications watch`, `project` and `host governance inspect` no longer fail on a notification severity or status, project source, action provider, prompt layer or quarantine reason, and `assistant materialize` no longer fails on an assistant concept type or intent that a newer daemon adds: the value reads as `unknown`, and `notifications watch` keeps streaming. ([#1339](https://github.com/zajca/pohunek/issues/1339))
- `pohunek host list` and `pohunek doctor` now say which `tailscale`, `netbird` or agent executable they found but refused to run, with the path and the reason (for example a directory other accounts can write), instead of reporting it as not installed. The error codes are unchanged. The recovery hint of a refused CLI points at the ownership and permissions it names instead of at installing it. On macOS, a directory dropped from the service `PATH` says whether others, a group other than `admin`, or an `admin`-group directory that the effective user does not own or that root looks up made it unsafe. ([#1583](https://github.com/zajca/pohunek/issues/1583))
- The Linux (glibc) daemon limits its malloc arenas to two at startup, which keeps its memory use near the size of its live data under heavy session churn (about 100 MB instead of 330 MB with 400 live sessions in the soak behind #1672, on a host with transparent huge pages set to `always`). Set `MALLOC_ARENA_MAX=<n>` (or `GLIBC_TUNABLES=glibc.malloc.arena_max=<n>`) in the daemon's environment to choose another limit; the daemon then leaves the allocator alone. Other platforms are unchanged. ([#1672](https://github.com/zajca/pohunek/issues/1672))
- A refused `service upgrade` or `install` that lists only stopped sessions now says "N stopped session(s) have unverified runtime or recovery" instead of "0 live session(s), N stopped session(s) have unverified runtime or recovery". ([#1771](https://github.com/zajca/pohunek/issues/1771))
- `pohunek assistant` and `cargo xtask docs check` refuse an `assistant/system.md` that holds a carriage return which is not part of a CRLF line ending, on any line, and name the line, instead of parsing the text after it as part of the same rule. ([#1882](https://github.com/zajca/pohunek/issues/1882))

### Fixed

- Idle stop no longer stops a session that has opted in while its agent still has live background work: a background subagent, workflow, shell, monitor or MCP task listed in the session's `background` snapshot holds the stop, and the idle time counts a full limit from the moment that work ends. The reported `activity` is unchanged (`idle` once the turn ends), teammates and provider-internal tasks do not hold, and Codex sessions behave as before. ([#495](https://github.com/zajca/pohunek/issues/495))
- A package runtime that reports a notification under its own id now ranks as a hook provider, so its attention report upgrades the daemon's record of the same moment instead of creating a second one. The daemon marks such a record with the new `hook_admitted` field, and the notification store moves to format 2: a daemon of this version reads format 1 stores unchanged, and an older daemon that reads a format 2 store ignores the field and ranks those records by provider name. ([#899](https://github.com/zajca/pohunek/issues/899))
- `notification.create` now refuses a report from a hook provider (`shell`, `codex`, `claude`, `hermes`, `muse`) for a session id the daemon neither holds nor is launching with `hook_not_admitted`, so no provider-ranked record is stored for an id the daemon cannot check against a hook schema. Reports from other producers, and identity reports for unknown sessions, are unchanged. ([#899](https://github.com/zajca/pohunek/issues/899))
- A Codex subagent that finished a turn and got a follow-up task (or was resumed) is now recorded again when that turn ends: its row takes a new revision and finish time, so `session` subagent views and events show the new turn. Before, only the child's first turn changed its row. The stream is recreated only when the set of transcript roots or a root's canonical path changes, after the event queue overflowed, and by a full rebuild every 10 minutes that heals a stream that never started or went silent; until then a change that is not delivered live is still indexed by the next 30 s pass. A runtime that a profile, session or integration uses and the release catalog lists more than once still stops setup before any change, and a runtime only the detection found and the catalog lists twice no longer stops it (`official_package_listed_more_than_once` and `catalog_lists_runtime_more_than_once` replace the shared gap code for that case). `package.bind_profile` takes an optional `expected_previous` pin (advertised as `package_bind_profile_expected_supported`) and refuses a changed pin with `package_profile_pin_changed`; `pohunek setup` and `pohunek plugin profile migrate --yes` send the pin they showed, so a profile pinned since is no longer overwritten, and against a daemon that cannot check it they print a note. ([#1159](https://github.com/zajca/pohunek/issues/1159))

Piped input is finished by closing only the write half, and the client keeps showing output until the daemon closes the stream once the program's terminal accepted the input; output still queued at that point may not be shown. A daemon attach also ends when a Unix socket client disconnects while its input waits for the program. A previous-release `pohunek attach` that pipes input into a slow program, and TS SDK clients (which cannot half-close), end their input with a complete close, which a Unix-socket daemon now treats as a disconnect: input the terminal had not accepted is dropped. ([#1160](https://github.com/zajca/pohunek/issues/1160))

The `SessionStart` hook also leaves `hook_started` and `hook_finished` lines in the hook failure trace, so a hook killed after the interpreter began shows as started without a finish. The managed hook assets are integration version 16: existing installs keep the old behaviour until the integration is reinstalled (`pohunek service upgrade` or `pohunek integration install`), and `integration status` reports them `outdated` until then. A hook killed while `python3` itself is still starting, as on the first start through the Xcode shim, leaves a `pohunek-hooks.jsonl.start.<suffix>` marker file beside the trace, which the next `SessionStart` run removes after an hour; pinning the interpreter is #1810. A missing active version directory is reported with the same code instead of `service_io_failed`, and so do the service upgrade, rollback and setup checks of an installed version. `pohunek service uninstall` no longer starts a stopped daemon from an active version directory that fails that check, so removing the installation does not run the untrusted `pohunekd`. ([#1360](https://github.com/zajca/pohunek/issues/1360))

A resize, a stop or an observation request is served while the delay runs, and attach keystrokes are no longer queued behind it. The text is still typed first and Enter follows after at least the configured delay. ([#1369](https://github.com/zajca/pohunek/issues/1369))
- A slow attach client no longer delays its own typing. When a remote link or a loaded host takes the agent's output slowly, keystrokes still reach the agent without waiting for the output to be written, and output the client cannot keep up with is replaced by a fresh repaint of the screen instead of piling up in memory. ([#1370](https://github.com/zajca/pohunek/issues/1370))

The provider status command now runs under one deadline, `status_timeout_secs` in `overlays.toml` (default 10, range 1 to 120 seconds), and is killed with everything it started when the deadline passes. An address that the provider lists for more than one peer, or for this machine, is no longer used for routing: selecting those peers fails as `overlay_host_ambiguous`, and `host list` shows them as candidates without an address and with the reason `address_ambiguous`. ([#1565](https://github.com/zajca/pohunek/issues/1565))

An existing service keeps its recorded `PATH` until `pohunek service refresh-path`; afterwards a Homebrew `git` earlier in the `PATH` shadows `/usr/bin/git`, as in your shell. Linux is unchanged. ([#1682](https://github.com/zajca/pohunek/issues/1682))

- The daemon now exits inside `daemon_exit_timeout_ms` even when a blocking store write never returns: it drops its async runtime through a 500 ms bound, logs a warning and exits, and the registry shutdown log names the stuck write. ([#1725](https://github.com/zajca/pohunek/issues/1725))

([#1767](https://github.com/zajca/pohunek/issues/1767))

Previously the connection tasks were not tracked, so a client saw the connection drop when the runtime was dropped, and a request could start after the stop signal. ## 0.38.1 - 2026-10-28

### Added

- `pohunek host command run <host> <package> <command>` runs a command an installed package declared, on the local daemon or an overlay peer, with `--timeout-ms`, `--max-output-bytes` and `--json`. It prints the program's stdout verbatim and exits 0; each `command_*` error exits with a status of its own (40 to 51, listed in `docs/cli.md`), and `command_unsupported` (40) reports a daemon without the method. The command takes no argument, environment variable, working directory or input. ([#1690](https://github.com/zajca/pohunek/issues/1690))
- An installed package can declare commands in `[commands.<name>]`, and `command.run` runs one on the daemon host: a fixed program of the verified package root with a cleared environment, a 60 s and 128 KiB limit, and the program's stdout returned verbatim. The local socket may call every declared command and an overlay peer only a command declared `peers`; installing a package that declares commands needs `accept_commands`. The TypeScript SDK has `runCommand`, which reports `command_unsupported` against a daemon without the method. ([#1690](https://github.com/zajca/pohunek/issues/1690))

## 0.38.0 - 2026-10-28

### Added

- A runtime descriptor can list core capabilities in a top-level `requires` array. The core refuses a descriptor that needs a capability it does not implement, or that uses a gated key without it, with `runtime_feature_unsupported`. ([#1612](https://github.com/zajca/pohunek/issues/1612))
- Runtime packages can describe Muse Code and other out-of-tree runtimes: numeric `1.4.13-R2` version probes (`version-probe-revision-v1`), literal `[launch_env]` flags from a closed set (`launch-env-v1`), a config home below a variable's value (`config-home-subdir-v1`), session logs below a data root read with the `muse-session-v1` parser (`transcripts-data-root-v1`), and the `muse-hook-v1` hook handler with a session-private managed hooks overlay (`integration-muse-hook-v1`). The Muse hook payload fixtures are derived from documentation and marked unverified. ([#1645](https://github.com/zajca/pohunek/issues/1645)) ([#1648](https://github.com/zajca/pohunek/issues/1648)) ([#1649](https://github.com/zajca/pohunek/issues/1649)) ([#1667](https://github.com/zajca/pohunek/issues/1667))
- An integration handler can contribute per-launch input (environment pairs, root-position arguments and private files) that core validates and applies to every create, resume and fork without storing it in the resume snapshot. A refused contribution fails the launch with `runtime/launch_input_invalid` or `runtime/launch_input_unavailable`. ([#1648](https://github.com/zajca/pohunek/issues/1648))
- `session.new` accepts `secret_env`, a map of variable name to value for the agent process. The host profile declares the names (`secret_env = ["NAME"]`) and the request supplies only the values, which are never persisted, listed or logged, so resume, fork and relay launches of such a profile fail with `secret_env_missing`. Clients check the new `HostCapabilities.session_new_secret_env_supported` first. ([#1691](https://github.com/zajca/pohunek/issues/1691))
- A package descriptor can declare commands (`[commands.<name>]` with `program`, `args` and `expose = "local" | "peers"`) behind `requires = ["package-commands-v1"]`. Installing such a package needs the `accept_commands` opt-in, advertised as `HostCapabilities.package_install_commands_supported`; without it the request is refused with `package_commands_client_unsupported`. The install review shows every command, and nothing runs yet: `command.run` arrives in 0.38.1. ([#1690](https://github.com/zajca/pohunek/issues/1690))
- On Linux the worker journals its cgroup path (`worker_control_group`, optional, no schema bump). When the lost-runtime sweep of `session rm` meets a process with an unreadable environment that lies outside the `user@<uid>.service` cgroup subtree of that path (such as a Docker scope or a logind session scope), it ignores the process instead of refusing with `runtime_supervision_ambiguous`. A hidden process inside the subtree, such as a `systemd-run --user --scope` unit, still makes `session rm` refuse, as does a worker that journaled no control group. ([#186](https://github.com/zajca/pohunek/issues/186))

### Changed

- The daemon now stops its session registry's background work before it exits, bounded by the optional `deadlines.registry_shutdown_ms` key of `service.toml` (1 to 600000 ms, 5000 ms when absent), and refuses store writes made after that, and a worker no longer rewrites its journal after the terminal outcome is committed except to record the terminal acknowledgement. ([#1592](https://github.com/zajca/pohunek/issues/1592))

## 0.37.1 - 2026-10-27

### Fixed

- `host.inspect` no longer takes seconds on a host with many agent runtimes and a large daemon: version probes spawn without `pre_exec` (so their cost no longer grows with the daemon's memory), run once per distinct program in parallel on a blocking thread, and are cached by the program's file identity for the optional `[inventory]` lifetimes of `service.toml`. `host.inspect` takes an optional `skip_runtime_probes` parameter that answers only the capability flags, which `pohunek session new --cwd`, `--from-remote` and `--input-ack-timeout-ms` now use for their capability check. The Rust `HostInspect` method keeps its `()` parameters; `Client::host_inspect_with` sends the new parameters. The TypeScript SDK types them as `HostInspectParams | null`. ([#1388](https://github.com/zajca/pohunek/issues/1388))
