`project.actions` and the daemon's `host.discover` reply are hard-bounded at 3200 actions and 1500 peer records respectively and checked against the control-line limit: above either bound the daemon answers the typed `project_actions_too_large` / `host_discover_too_large` error instead of a frame the client refuses. All config names (action, template, prompt, agent, profile, …) are capped at 128 bytes — now the shared `MAX_CONFIG_NAME_BYTES` constant in `crates/protocol`, enforced identically by the daemon's `validate_name` and the CLI's profile-name check, which previously allowed 250 bytes on its own: an over-cap name is refused with `invalid_name` on both sides and never echoed, so even a name longer than a control line gets a frameable error reply. Compatibility: profile, `spawn_profile`, action and template names longer than 128 bytes were accepted before (up to the 250-byte file-name bound a profile file can have) and stop loading after this change — rename such files to a name of at most 128 bytes. `package.remove_profile` answers `invalid_name` (never `package_profile_not_found`) when a file with an over-cap name is on disk. `host.discover` peer records cap their supplied fields (`name`, `fqdn`, `peer_id`, `daemon_version`) at build time, reporting an over-cap field through the record's bounded `reason` (`identity_too_large`, `daemon_version_too_large`, or the local probe codes `local_probe_timeout`, `local_probe_failed`, `local_daemon_error`) instead of echoing it. `package.list` documents its existing `MAX_PACKAGES` (1024) registry bound. ([#1110](https://github.com/zajca/pohunek/issues/1110))
