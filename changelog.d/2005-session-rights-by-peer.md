kind: security

The daemon now places each local caller by its kernel-attested process: a `pohunek` command run inside a session's process tree can stop, resume, remove, rename, label, resize, type into or attach to only that session's descendants, plus `session.input` to its own parent while the parent is not waiting on a dialog. Anything else is refused with `session_right_denied` (`reason=not_descendant`, `parent_blocked` or `unknown_caller`) and an audit refusal line, so a worker can no longer reach a sibling or its manager's lifecycle through the owner socket. The owner's own terminal, services outside every session tree and `shell` sessions keep owner rights. A process below a session's worker is attributed to that session from the moment the worker starts, on a first launch and on a resume alike, and the daemon records the worker's identity so a restart attributes it again even while the worker is unreachable. A live session whose worker the daemon has no record of and cannot place by control group makes `pohunek doctor` fail the `session_rights` check and refuses callers no root attributes as `unattributed_caller`. This is a guardrail, not a wall: a process of the same user that leaves the session tree (a double fork, or `systemd-run --user --scope` on Linux) keeps owner rights, and `pohunek doctor` reports the `session_rights` check that says so. Tooling that mutates sessions it did not spawn from inside a session, such as a manager sending input to another manager's worker, needs a profile with `[rights] owner_equivalent = true`, or must run from the owner's terminal or a service outside the session tree. ([#2005](https://github.com/zajca/pohunek/issues/2005))
