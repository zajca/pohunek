`pohunek service refresh-path [--dry-run] [--accept-runtime-loss] [--json]` re-records the executable search path from your login shell, as install would record it now, prints the directories it adds and removes, and replaces the daemon job with it, so the running daemon gets the new `PATH` at once. Use it after installing an agent prefix later or after a Nix profile update moved the profile link. The path in `service.toml` and the daemon job change together in one journaled transaction or not at all; only the daemon restarts, worker jobs keep running. The new daemon's adoption verdict is taken first, as for an upgrade: live sessions it would not adopt refuse the run unless `--accept-runtime-loss` is given, which records nothing. Readiness requires a new daemon process, and a replacement or readiness failure restores the previous path and job. An interrupted run is resumed by rerunning the command, or rolled back; from the replacement step on, the pending record blocks `install` and `upgrade` (`service_refresh_pending`) until `refresh-path` completes or rolls it back. A login shell that fails, hangs or prints junk never replaces the recorded path. New error codes: `service_daemon_job_missing`, `service_refresh_config_changed`, `service_refresh_pending`.
