`pohunek service refresh-path [--accept-runtime-loss]` also replaces the daemon job with the re-recorded search path, so the running daemon gets the new `PATH` at once. The path in `service.toml` and the daemon job change together in one journaled transaction or not at all; only the daemon restarts and worker jobs keep running. The new daemon's adoption verdict is taken first, as for an upgrade: live sessions it would not adopt refuse the run unless `--accept-runtime-loss` is given, which records nothing. Readiness requires a new daemon process, and a replacement or readiness failure restores the previous path and job. An interrupted run is resumed by rerunning the command, or rolled back; from the replacement step on, the pending record blocks `install` and `upgrade` until `refresh-path` completes or rolls it back. In production the daemon replacement runs on macOS only. New error codes: `service_daemon_job_missing` (no registered daemon job), `service_refresh_config_changed` (`service.toml` was edited while a refresh was pending) and `service_refresh_pending` (a pending refresh blocks the command).
